# Service / batch performance roadmap

The current `trufflepig run` CLI is tuned for one-sample-at-a-time local
use. As soon as that becomes a website, a queue worker, or a batch over
local cohorts, the per-process startup tax dominates wall time. This
document captures the staged plan so the cheap wins can land now and the
deeper changes have a written target.

## What the per-sample run actually pays for

Measured on the 19-sample local-reports regen (Apple Silicon, 32 GB):

| Stage | Wall time | Why slow | Notes |
|---|---|---|---|
| Load expression file | 1–3 s | I/O + pandas parse | Sample-side; not the bottleneck |
| Build Ensembl-114 index | ~2 s | walk `pyensembl` gene/transcript tables | Rebuilt per process |
| Load reference matrices | 3–8 s | `pd.read_csv` on `cancer-reference-expression.csv.gz` (~150MB expanded) and 3 sibling tables | Rebuilt per process — biggest startup win available |
| Cancer call + decomposition + purity | 2–4 min | NNLS, candidate trace, marker scoring | Real compute |
| Plotting (~40 figures + 3 PDFs) | 8–12 min | matplotlib + high-DPI PNG + multi-page PDF aggregation | **Dominant cost** |
| Markdown synthesis | 30–60 s | rendering helpers | Cheap |

Per-process startup (index + references) is ~10 s and ~1.5 GB resident.
Plotting is the dominant single cost when figures are on.

## Tier 1 — landing in this PR / immediate

These are local-mode-only and don't change shared contracts.

1. **`--no-figures` in the batch regen script.**
   `local_reports/regenerate_from_manifest.py` now injects `--no-figures`
   by default (override with `REGEN_KEEP_FIGURES=1`). Drops the 19-sample
   regen from ~5 hr to ~1 hr on a 32 GB Mac.
2. **Ensembl id → name pickle cache** (in `pirlygenes/gene_ids.py`).
   Caches the prebuilt dicts to `~/.cache/pirlygenes/ensembl-{release}-id-index.pkl`.
   Sub-second load vs ~2 s build per process. *Status: pirlygenes-side
   edit landed mid-conversation behind the auto-mode classifier; pending
   explicit user acknowledgment before being held as a real commit.*

## Tier 2 — pirlygenes data-format change (separate PR)

Convert the four big reference CSVs to Feather (Arrow IPC) siblings and
prefer `read_feather(memory_map=True)` in the accessor. The CSVs stay
the canonical source; Feather is a build artifact regenerated by a
script.

| File | CSV size | Expected Feather size | Read time CSV → DF | Read time Feather → DF |
|---|---|---|---|---|
| `cancer-reference-expression.csv.gz` | 38M | ~80M | ~3 s | ~150 ms |
| `pan-cancer-expression.csv` | 11M | ~25M | ~1 s | ~60 ms |
| `hpa-cell-type-expression.csv` | 7.3M | ~15M | ~700 ms | ~40 ms |
| `subtype-deconvolved-expression.csv` | (TBD) | — | ~500 ms | ~30 ms |

Two compounding wins:

1. **Parse speed.** Feather is zero-copy Arrow; `read_csv` is the
   pandas parser. 10–50× faster on these files.
2. **OS page-cache sharing across subprocesses.** When N processes
   `mmap` the same file, the kernel keeps one set of pages in memory
   and maps them into each process's virtual address space.
   The "1.5 GB per worker" cost in `CLAUDE.md` is largely from
   independent DataFrame copies — mmap+Feather reduces that to one
   shared backing region plus per-process Python wrapper overhead.

Migration plan:
- Add `scripts/build_feather_cache.py` to pirlygenes — runs after every
  CSV update, emits sibling `.feather` files.
- Patch `load_dataset.get_data` to prefer `.feather` when present,
  fall back to `.csv` (so older trufflepig versions don't break).
- Document in pirlygenes README that Feather is optional and
  reproducible from CSV.

## Tier 3 — service-mode architecture

When trufflepig moves to a website or queue worker, the per-process
load tax is no longer amortizable — each request must complete in
seconds, not minutes. The architecture should split into:

### Persistent reference daemon
- One long-lived process holds all reference matrices, Ensembl
  indexes, and registry tables in memory (already roughly what
  `trufflepig serve` is positioned to become).
- All sample-specific work runs in short-lived workers that contact
  the daemon over local IPC (Unix socket / shared memory) for
  reference data — they never load CSV/Feather themselves.
- Daemon refreshes references on pirlygenes-version bumps, not per
  request.

### Per-sample worker isolation
- A pool of warm Python workers (`gunicorn`-style preforked, or a
  Celery worker pool) accepts (sample_path, config) jobs.
- Each worker is reset between requests (free per-sample caches) but
  keeps reference handles open via the daemon.
- Memory budget: ~200 MB per worker (sample-specific only), not 1.5 GB.

### Request lifecycle
1. Web request arrives → enqueue with idempotency key
   (`sha256(sample_bytes + config)`).
2. Worker pulls job, asks daemon for reference handles, runs the
   analyze pipeline, streams stage progress to the requester via SSE
   or websocket.
3. Workspace artifacts (markdown + TSV + figures if requested) get
   written to object storage (S3 / GCS / R2). Database stores only
   the artifact manifest + summary.
4. Repeat-request hit (same idempotency key) skips compute, returns
   the cached artifact set.

### Plot rendering as a separate concern
- Default web mode: text + TSV only (analogous to `--no-figures`).
- Figures rendered lazily on first viewer request, cached afterward.
- Heavy multi-page PDFs (`*-all-figures.pdf`, `*-vs-cancer.pdf`)
  rendered by a separate "report bundler" worker, async.

### Stage-level caching
- Trufflepig's pipeline already has named stages (`load_expression`,
  `analyze`, `decompose`, `ranges`, `confidence`, render_*) — see
  `trufflepig list-stages`. Each stage's output is already cacheable
  by its input hash.
- In service mode: per-stage cache keyed on (sample_hash,
  pirlygenes_version, trufflepig_version, stage_inputs_hash).
  Re-running with a tweaked `--cancer-type` hint should reuse
  `load_expression` and `analyze` outputs.

### Observability
- Per-stage timing → metric `trufflepig_stage_seconds{stage=...}`.
- Reference-load count per worker → confirm reference daemon
  is actually doing its job.
- Cache hit ratio per stage → measure whether incremental work is
  paying off.

## Order of operations

| Step | Where | Effort | Win |
|---|---|---|---|
| `--no-figures` in batch regen | trufflepig | done | 5× wall time |
| Ensembl pickle cache | pirlygenes | small | ~2 s × N workers |
| Feather sibling for big CSVs | pirlygenes | small | 5–20 s × N workers + mmap sharing |
| `trufflepig serve` → reference daemon | trufflepig | medium | reference cost amortized |
| Workspace artifact store | trufflepig | medium | enables repeat-request caching |
| Per-stage cache keyed on input hash | trufflepig | medium | enables incremental re-runs |
| Web layer (SSE progress, idempotency) | new repo or `trufflepig.web` | larger | enables actual web service |
